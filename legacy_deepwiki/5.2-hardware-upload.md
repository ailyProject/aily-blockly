This document describes the hardware upload system in Aily Blockly, which handles flashing compiled code to physical hardware devices. The system supports multiple transport layers including serial upload (via `arduino-cli` and `esptool`), debugger upload (via `probe-rs`), and wireless firmware transfer (via BLE OTA).

## Upload Process Overview

The hardware upload system is managed by the `_UploaderService`, which coordinates with the `WorkflowService` to manage state and the `CmdService` to execute external flashing tools.

## Serial Upload & 1200bps Touch

For many Arduino-compatible boards (like Seeed XIAO series), the device must be put into bootloader mode before flashing. Aily Blockly automates this using the \"1200bps touch\" technique.

1.  **1200bps Touch**: The service opens the serial port at 1200 baud and then closes it. This signals the microcontroller's CDC stack to reset into the bootloader [child/scripts/upload.js:82-115]().
2.  **Port Hunting**: After the reset, the original port often disappears and a new port appears. The system polls for this change using `waitForNewPort()` [child/scripts/upload.js:122-139]().
3.  **Command Execution**: Once the bootloader port is identified, the system executes the upload command (e.g., `esptool` for ESP32 or `arduino-cli` for others) [child/scripts/upload.js:237-260]().

Sources: [child/scripts/upload.js:82-139](), [src/app/services/serial.service.ts:20-88]()

## Debugger Upload (probe-rs)

For ARM-based boards (STM32, nRF52), the IDE supports uploading via hardware debuggers (DAPLink, J-Link) using the `probe-rs` utility.

-   **Detection**: The `SerialService` identifies these devices as `type: 'debugger'` [src/app/services/serial.service.ts:13-102]().
-   **Execution**: When a debugger is selected, the upload script switches from serial-based protocols to `probe-rs download` commands.

## BLE OTA Firmware Transfer

The `UploaderBleService` provides a specialized transport for Over-The-Air (OTA) updates via Bluetooth Low Energy. This is used for devices that lack a physical USB connection or for remote updates.

```mermaid

```

Sources: [src/app/services/uploader-ble.service.ts:6-18](), [src/app/services/uploader-ble.service.ts:75-84](), [src/app/services/uploader-ble.service.ts:114-134]()

The protocol uses a chunked transfer method:
-   **Sector Size**: 4096 bytes [src/app/services/uploader-ble.service.ts:11]().
-   **Acknowledgements**: The device sends `CMD_ACK` for every sector received to ensure integrity [src/app/services/uploader-ble.service.ts:17]().

## SoftDevice Flashing Workflow

For nRF5-based boards, a \"SoftDevice\" (Bluetooth stack) must often be flashed separately from the application code.

-   **Action**: Triggered via the `flash-softdevice` IPC action [src/app/editors/blockly-editor/services/uploader.service.ts:99-107]().
-   **Implementation**: The `_UploaderService` calls `flashSoftdevice()`, which uses `probe-rs` or `nrfjprog` to write the specific hex file to the device's reserved memory regions.

Sources: [src/app/editors/blockly-editor/services/uploader.service.ts:98-108]()

## Progress Tracking System

The `_UploaderService` uses a suite of regex patterns to parse the stdout of various CLI tools (esptool, arduino-cli, etc.) and convert them into a unified 0-100% progress bar for the UI.

## ESP32 Specialized Flashing (esptool-py)

The `EsptoolPyService` manages the Python-based `esptool` environment. It handles:
1.  **Detection**: Scanning `node_modules/@aily-project/tool-esptool_py` for the executable [src/app/services/esptool-py.service.ts:117-135]().
2.  **Path Resolution**: Finding the correct `python` or `esptool.exe` path across Windows and macOS [src/app/services/esptool-py.service.ts:197-208]().
3.  **Multi-File Flash**: ESP32 requires flashing multiple binaries (bootloader, partition table, app, ota_data) at specific offsets [src/app/services/esptool-py.service.ts:28-36]().

Sources: [src/app/services/esptool-py.service.ts:45-53](), [src/app/services/esptool-py.service.ts:80-110]()
