# GLOBAL

本文件作为当前项目的全局提示词指引，适用于生成代码、重构代码、拆分模块和补充实现。

## 代码生成与重构限制

- 单文件不要超过 180 行；超过就必须继续拆分模块、函数、组件或辅助文件。
- 能写成无状态逻辑的，就不要写成 class。
- 优先使用无状态函数组织逻辑。
- 当函数参数超过 3 个时，改用对象参数。
- 不允许为了让 TypeScript 代码先跑起来而随便使用 `any` 或 `unknown`；不要用它们逃避类型设计。
- 代码必须优先定义清晰的类型、接口、输入输出契约，再基于这些类型实现逻辑；先有类型，再有代码。
- 不要为了追求开发速度而忽略类型完备性；代码应建立在类型约束之上，这样才足够健壮、可验证、可维护。
- 如果运行时边界不可避免地产生 `unknown`，必须立刻通过类型守卫、schema 校验或显式解析把它收窄后再继续传递。
- `any` 只能作为极少数例外场景下的最后手段，不能作为日常实现工具。
- 复杂函数优先补中文注释，说明函数职责、关键输入输出、边界条件和必要的副作用。
- 注释应帮助理解意图和验证实现，不要只机械复述代码表面行为；简单函数不要为满足形式而堆注释。
- 数据交互默认使用 `hono` / `trpc` / `erpc` 这一套组合，参考 `/Users/xiewendao/Documents/Projects/polywise/` 的实现方式。
- HTTP 服务入口优先使用 `hono`；跨端数据契约优先使用 `trpc`；Electron 主进程与渲染进程通信优先使用 `erpc`。
- 不要随意引入自定义 REST 风格约定、松散类型的 fetch 封装、手写 RPC 协议或零散 IPC channel 来替代这套统一边界。
- 不要新增以 RxJS 为核心的状态管理或数据流组织；能用 Angular Signals、普通函数和简单可读状态组织解决的，就不要额外引入 RxJS 方案。
- 如果框架、现有依赖或明确的边界接口天然使用 RxJS，可以在该边界内使用，但不要把它继续扩散成项目默认状态模型。
- 以上限制的目标是让 AI 更容易持续产出可维护、可理解、可拆分的代码。

## 命名与风格

- 变量命名统一使用驼峰命名法。
- 组件命名统一遵循 Angular 风格，使用中横线形式组织 selector、文件名和相关模块命名。
- 编写代码时，优先参考同级目录下相似模块的写法、结构和命名风格，保持风格统一。
- 优先使用文件夹下的 `index.ts` 做 barrel 导出，统一对外暴露稳定入口，减少 import 语句的规模和路径噪音。
- 新增子目录如果会被外部多个模块消费，应同步考虑是否提供对应的 `index.ts` 作为目录级导出入口。
- 样式统一使用 CSS，不使用 SCSS。
- 当前项目样式基础设施为 CSS + PostCSS（已安装相关嵌套语法支持）+ Tailwind CSS。
- 状态管理方案仅允许使用 Angular 22 正式推出的 signal 相关能力，例如 signal、computed、linkedSignal、input、model、output 等。
- 不要引入旧式状态管理方案或额外响应式状态库；优先使用 Angular signal 体系以获得更高性能和更清晰的数据流。
- 前端 AI UI 集成默认使用 `@ai-sdk/angular`，优先通过 Angular 原生方式承接流式状态、消息渲染和相关 UI 逻辑。

## 格式化基线

- 代码格式化以仓库根目录的 `.prettierrc` 为唯一准绳，不要再额外口头约定一套会和 formatter 冲突的缩进、分号或尾随逗号规则。
- 如果文档描述与 `.prettierrc`、`.prettierignore` 或自动格式化结果冲突，以这些配置文件和实际格式化结果为准。

## 实施原则

- 新增实现前，先观察相邻目录和同类模块，不要凭空发明完全不同的结构。
- 如果同级目录已有稳定模式，优先复用同样的拆分方式、命名方式和文件组织方式。
- 如果现有模块过大或过乱，不要继续复制问题，应在满足本文件限制的前提下做渐进式优化。

## “分形”代码划分规则

- 代码必须允许按职责、分形、子域、运行时边界持续拆分，目录层级不设硬上限；需要时可以继续添加更深的文件夹。
- 不要因为“当前层级已经够深”就停止拆分；只要职责边界还能继续变清晰，就应继续下钻。
- 拆分优先按稳定职责划分，不按一次性实现细节划分。
- 优先形成长期有效的结构节点，例如：`components`、`pages`、`layout`、`runtime`、`context`、`models`、`types`、`utils`、`agent`、`build`、`project`、`hardware` 这类稳定边界。
- 如果某个模块继续膨胀，可以在该模块内部继续做下一层“分形”拆分，例如：`feature/context`、`feature/model`、`feature/components`、`feature/utils`、`feature/runtime`。
- 可以同时按“功能域 + 职责域”组合拆分；不要把所有代码都压回单层目录。
- 文件夹说明应体现责任边界，而不是只体现技术实现细节。
- 不要为一次性的零散叶子节点过度造目录，但一旦某个子域会持续增长，就应该尽早独立成更深层目录。
- 不要把不相关逻辑塞进同一个 `utils`、`services`、`components` 或单个 feature 文件夹里；当内部职责变多时，继续分形。
- 目录划分应优先服务可维护性、可读性、可替换性和 AI 持续生成能力，而不是追求表面上的“目录少”。
