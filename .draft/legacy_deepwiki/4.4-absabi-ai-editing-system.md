This page details the Aily Block Syntax (ABS) Domain Specific Language (DSL) used by the AI agent to interact with Blockly workspaces, the Aily Blockly Interchange (ABI) JSON serialization format, the bidirectional conversion process between ABS and ABI, the incremental synchronization mechanism, and the block repair pipeline. These components collectively enable the AI agent to understand, generate, and modify Blockly programs effectively.

## Aily Block Syntax (ABS) DSL

The Aily Block Syntax (ABS) is a human-readable, indentation-based DSL designed to simplify the generation and modification of Blockly code by AI agents. It aims to reduce errors and improve readability compared to direct manipulation of Blockly's verbose JSON format. ABS supports variable definitions, block calls with parameters, and statement inputs, closely mirroring the visual structure of Blockly blocks.

### Syntax Overview

ABS uses a simple, line-oriented syntax:

- **Block Calls**: `block_type(param1, param2)` [src/app/tools/aily-chat/tools/getAbsSyntaxTool.ts:23-23]()
- **Empty Parameters**: `block_type()` [src/app/tools/aily-chat/tools/getAbsSyntaxTool.ts:24-24]()
- **Statement Inputs**: `@NAME:` followed by a newline and indented blocks [src/app/tools/aily-chat/tools/getAbsSyntaxTool.ts:27-27]()
- **Variable References**: `$varName` [src/app/tools/aily-chat/tools/getAbsSyntaxTool.ts:28-28]()

Parameters can be dropdown values (e.g., `Serial`, `HIGH`), text literals (e.g., `\"hello\"`), numbers (e.g., `9600`), variable references, or nested value blocks. A crucial rule is that parameters follow the `args0` definition order from the `block.json` file, which can interleave fields and value inputs [src/app/tools/aily-chat/tools/getAbsSyntaxTool.ts:41-46]().

### Example ABS Code

```abs
# Variable definition
@var count: int = 0

# Arduino main program
arduino_setup()
    serial_begin(Serial, 115200)
    oled_begin()

arduino_loop()
    serial_print(Serial, \"Count: \")
    serial_println(Serial, $count)
    math_change($count, 1)
    delay(1000)
```

[src/app/tools/aily-chat/tools/absParser.ts:8-22]()

This example demonstrates global variable definition (`@var`), root blocks (`arduino_setup`, `arduino_loop`), and nested statement and value blocks.

### Block Metadata for Parsing

The `BlocklyAbsParser` [src/app/tools/aily-chat/tools/absParser.ts:240-240]() relies on block metadata to correctly interpret ABS. This metadata includes information about field names, value input names, statement input names, and the order of arguments (`argsOrder`) [src/app/tools/aily-chat/tools/absParser.ts:81-88](). The system dynamically loads block definitions from project libraries to ensure up-to-date metadata [src/app/tools/aily-chat/tools/absParser.ts:101-115](). If dynamic loading fails, a fallback set of built-in block definitions is used. For blocks defined only in JavaScript, the parser can query Blockly's runtime to infer input structures by creating temporary block instances [src/app/tools/aily-chat/tools/absParser.ts:195-235]().

## Aily Blockly Interchange (ABI) JSON Serialization

The Aily Blockly Interchange (ABI) is the internal JSON serialization format for Blockly workspaces. It is essentially the standard Blockly serialization format (`Blockly.serialization.workspaces.save(workspace)`) with some additional metadata. This format is used for saving and loading projects, and for internal communication within the application.

The `BlockConfig` interface [src/app/tools/aily-chat/tools/editBlockTool.ts:71-90]() defines the structure of a block within the ABI format, including its type, ID, fields, inputs, position, and `extraState` for dynamic blocks (e.g., `itemCount` for `text_join`, `elseIfCount` for `controls_if`).

## Bidirectional ABS ↔ ABI Converter

The system includes a bidirectional converter that translates between the human-readable ABS DSL and the machine-readable ABI JSON format. This conversion is critical for enabling the AI agent to operate on Blockly workspaces.

### ABI to ABS Conversion

The `convertAbiToAbs` function [src/app/tools/aily-chat/tools/abiAbsConverter.ts:33-95]() takes an ABI JSON object and converts it into an ABS string. Key aspects of this conversion include:

- **Header Inclusion**: Optional inclusion of a descriptive header [src/app/tools/aily-chat/tools/abiAbsConverter.ts:45-58]().
- **Variable Handling**: Variables are registered internally for ID-to-name conversion but are not directly output as `@var` declarations in ABS. Instead, `variable_define` blocks are expected to handle C++ variable declarations [src/app/tools/aily-chat/tools/abiAbsConverter.ts:60-68]().
- **Block Sorting**: Blocks are sorted by their Y-coordinate (and then X-coordinate) to ensure the generated ABS reflects the visual layout of the workspace [src/app/tools/aily-chat/tools/abiAbsConverter.ts:75-80]().
- **Line Mapping**: The `convertAbiToAbsWithLineMap` function [src/app/tools/aily-chat/tools/abiAbsConverter.ts:100-162]() generates the ABS string along with a `blockLineMap` which maps each block's ID to its corresponding line range in the generated ABS. This map is crucial for AI agents to pinpoint specific blocks in the ABS for editing.

The `ConversionContext` class [src/app/tools/aily-chat/tools/abiAbsConverter.ts:167-178]() manages variables and tracks line numbers during the conversion process.

### ABS to ABI Conversion

The `convertAbsToAbi` function [src/app/tools/aily-chat/tools/abiAbsConverter.ts:400-400]() takes an ABS string and converts it into an ABI JSON object. This process involves:

1. **Parsing ABS**: The `BlocklyAbsParser` [src/app/tools/aily-chat/tools/absParser.ts:240-240]() first parses the ABS string into an intermediate `AbsParseResult` structure, which includes `rootBlocks` (BlockConfig objects) and `variables` [src/app/tools/aily-chat/tools/absParser.ts:63-66]().
2. **Block Reordering**: Root blocks are reordered before loading into Blockly. Function definition blocks (e.g., `custom_function_def`) are loaded first to ensure their mutators register functions, allowing function call blocks to correctly retrieve parameter information. `arduino_setup` and `arduino_loop` blocks are loaded last [src/app/tools/aily-chat/tools/syncAbsFileTool.ts:58-74]().
3. **Block Creation**: The parsed `BlockConfig` objects are then used to create actual Blockly blocks using `createBlockFromConfig` [src/app/tools/aily-chat/tools/syncAbsFileTool.ts:203-203](). This function handles the creation of blocks, their fields, inputs, and `extraState`.
4. **Variable Creation**: Variables defined in the ABS are created in the Blockly workspace.
5. **Connection Handling**: The parser also handles connections between blocks, including `next` connections and input connections.

## Incremental Workspace Synchronization

The `AbsAutoSyncService` [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:12-12]() manages the synchronization between the Blockly workspace and the `project.abs` file. This service ensures that changes made in the visual editor are reflected in the ABS file, and vice-versa, especially when the AI agent is involved.

### Synchronization Process

- **Export to ABS**: When the AI agent needs to read the current state of the workspace, or at the start of a session, the workspace's ABI JSON is converted to ABS and written to `project.abs` [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:145-171](). This process also generates a `blockLineMap` which is used to highlight blocks in the editor based on their ABS line numbers [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:132-133]().
- **Import from ABS**: When the AI agent modifies the `project.abs` file, the changes are imported back into the Blockly workspace. The ABS content is parsed, converted to ABI, and then applied to the active Blockly workspace [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:240-252]().
- **Version Control**: While the `AbsAutoSyncService` previously handled version history, this functionality has been migrated to `EditCheckpointService` [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:8-9](). However, the `syncAbsFileHandler` [src/app/tools/aily-chat/tools/syncAbsFileTool.ts:84-84]() still includes logic to save a version of the workspace before AI modifications, acting as a backup [src/app/tools/aily-chat/tools/syncAbsFileTool.ts:221-230]().
- **Concurrency Control**: A `isSyncing` flag [src/app/tools/aily-chat/services/abs-auto-sync.service.ts:36-36]() prevents re-entrant synchronization calls, ensuring data consistency.

## Block Repair Pipeline

The `blockConfigFixer.ts` [src/app/tools/aily-chat/tools/blockConfigFixer.ts:1-12]() module implements a two-stage repair pipeline for `BlockConfig` objects, addressing common issues that arise from AI-generated or manually edited JSON:

1.  **JSON Syntax Repair**: Uses `jsonrepair` to fix basic syntax errors like missing braces or quotes [src/app/tools/aily-chat/tools/blockConfigFixer.ts:10-10]().
2.  **Structural Semantic Repair**: Addresses logical inconsistencies that `jsonrepair` might introduce, such as incorrect nesting of inputs. For example, if `DO0` is mistakenly nested inside `IF0` in a `controls_if` block, this stage corrects the structure [src/app/tools/aily-chat/tools/blockConfigFixer.ts:11-11]().

The `fixBlockConfig` function [src/app/tools/aily-chat/tools/editBlockTool.ts:5-5]() is the entry point for this pipeline. It takes a potentially malformed `BlockConfig` and attempts to return a valid one.

### Dynamic Input Detection

A key part of the structural repair is the dynamic detection of block input information. The `getBlockInputInfo` function [src/app/tools/aily-chat/tools/blockConfigFixer.ts:77-127]() creates temporary Blockly blocks to inspect their `inputList` and determine valid statement, value, and dummy input names. This information is cached to improve performance [src/app/tools/aily-chat/tools/blockConfigFixer.ts:60-64]().

For dynamic blocks like `controls_if` or `text_join`, the `getValidInputsForBlockType` function [src/app/tools/aily-chat/tools/blockConfigFixer.ts:139-236]() intelligently infers valid input names based on `extraState` properties (e.g., `elseIfCount`, `itemCount`) and known dynamic input patterns (e.g., `IF0`, `DO0`, `ADD0`). This allows the repair pipeline to correctly re-parent inputs that might have been misplaced during initial parsing.
