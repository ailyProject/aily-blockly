# 优化文件查找体验

## 1. 背景

`aily-blockly` 当前在 `aily-chat/aily-lex` 体系里已经提供了 `glob_search` 和 `grep_search` 两类工具，但实际体验仍然不稳定，尤其是在以下场景里比较明显：

- 用户只记得文件名的一部分，或者只记得一个模糊概念，而不是完整 glob。
- 模型需要先快速定位候选文件，再进入 `read_file` / `edit_file`。
- 仓库里存在空文件、配置文件、隐藏文件、非代码文本、目录级入口文件时，查找结果不完整。
- 模型需要自己判断该先用 `glob_search` 还是 `grep_search`，会产生额外推理成本。

这份报告的目标不是新增一套新的文件搜索体系，而是在保留 `glob_search` / `grep_search` 这套交互模型的前提下，优化它们的底层实现和提示词引导，让模型在更多场景下能更快打到高命中结果。

## 2. 现在的文件查找流程，以及文件查找的目标

### 2.1 文件查找的目标

当前文件查找服务的真实目标，是为模型和用户提供一个低成本的“候选文件定位”能力，支撑后续动作：

- 快速找到应该读取的文件。
- 在不打开大量文件的前提下收窄搜索范围。
- 在大型仓库里尽量快地返回少量高价值候选结果。
- 为后续 `read_file`、`edit_file`、`create_file`、`delete_file` 等工具提供入口。

换句话说，文件查找不是终点，而是整个代码理解和修改流程里的第一跳。

### 2.2 当前流程总览

当前链路不是直接由 `aily-lex` 自己决定，而是宿主在中间插入了一层 Blockly/Electron 搜索扩展。

主链路如下：

1. 模型调用 `glob_search` 或 `grep_search`。
2. `aily-lex` 的通用搜索层先尝试 `host.getExtension('search')`。
3. `aily-blockly` 在宿主侧注入 `searchFiles` / `searchText` 实现。
4. 如果宿主实现可用，`aily-lex` 就不会再走它自己的 `rg --files` / `rg grep` 路径。
5. 最终结果返回给模型，模型再决定是否继续 `read_file`。

## 3. 现在的文件查找流程有什么问题

### 3.1 `glob_search` 实际上不是“文件搜索”，而是“内容文件枚举 + JS 过滤”

这是当前最大的问题。

`listAllContentFiles()` 不是从文件系统枚举文件，而是执行：

```sh
rg -l --max-count=1 .
```

这个策略会天然偏向“非空、可被内容搜索命中的文本文件”，而不是“工作区中的所有候选文件”。因此以下对象可能天然缺失或表现不稳定：

- 空文件
- 部分隐藏文件
- 某些配置文件
- 部分非文本文件
- 目录本身
- 没有内容但路径很重要的入口文件

这会导致用户以“文件名思维”搜索时，结果和直觉不一致。

### 3.2 `glob_search` 的命中率依赖扫描顺序，结果稳定性不足

当前 `glob_search` 结果本质上是：

- 先拿到一批文件
- 再用 glob 正则过滤
- 截断返回前 N 个

这意味着结果质量很大程度取决于“扫描顺序 + 截断”，而不是“路径是否真正匹配得更好”。对于以下查询，命中率和稳定性都会受影响：

- `pin map`
- `search session`
- `config`
- `builder`
- 只记得文件名一部分或路径片段

在当前方案下，即使 glob 写得没问题，也可能因为候选集来源不对或截断过早，导致真正目标文件没有稳定出现在前面。

### 3.3 ignore 规则不统一

当前路径上至少有两套 ignore 语义：

- ripgrep 自己的 ignore 规则
- fallback 文件系统遍历里的手写忽略目录集合

手写忽略规则见：

- [src/app/tools/aily-chat/helpers/lex-agent-bootstrap.ts](/Users/xiewendao/Documents/aily/aily-blockly/src/app/tools/aily-chat/helpers/lex-agent-bootstrap.ts:2025)
- [../aily-lex/src/tools/common/search.ts](/Users/xiewendao/Documents/aily/aily-lex/src/tools/common/search.ts:102)

问题在于：

- 它们不能完整表达项目自己的 `.gitignore` / `.ignore` 语义。
- 前后两段逻辑的结果可能不一致。
- 用户很难预测“为什么这个文件有时能搜到，有时搜不到”。

### 3.4 工具语义和实际行为不完全一致

工具描述里写了：

- `glob_tool` “Returns matching file paths sorted by modification time”
- `grep_tool` 兼具文件模式和内容模式

但从当前宿主实现看：

- 没有按修改时间排序。
- `glob_search` 的核心实现不是“按文件名查找所有文件”，而是“内容文件候选集过滤”。
- `grep_search` 侧还存在宿主实现与 `aily-lex` 输入能力不完全对齐的问题，例如 `includeIgnoredFiles` 并没有在 Blockly 宿主搜索扩展里完整体现。

这会导致工具文档、模型预期和真实行为之间出现偏差。

### 3.5 模型需要自己决定“先 glob 还是先 grep”，认知成本偏高

目前 agent 提示词倾向于这样分工：

- 只知道文件名模式时用 `glob_search`
- 要按内容搜时用 `grep_search`

这套思路在“工具使用者是工程师”时成立，但对模型来说并不是最优交互形态。原因是：

- 用户的问题往往是模糊的，不是标准 glob 查询。
- 模型要先推理“这是文件名问题还是内容问题”。
- 推理错误会直接导致首轮搜索质量下降。

本质上，这是把“搜索策略”的责任推给了模型，而不是由系统自己提供更强的默认搜索器。

### 3.6 提示词对高命中搜索的引导还不够具体

当前提示词虽然区分了 `glob_search` 和 `grep_search` 的用途，但对“如何提高首轮命中率”引导还不够细。

缺少的引导主要包括：

- 当用户只给概念词时，应先把概念拆成更适合路径匹配的 glob 片段。
- 什么时候应该先 `glob_search` 收窄文件集，再 `grep_search` 搜内容。
- `grep_search` 的 `includePattern` 应该如何配合 `glob_search` 结果一起使用。
- 对常见配置文件、文档文件、测试文件，应该优先尝试哪些 glob 模式。
- 当首轮查询无结果时，应该如何逐步放宽 pattern，而不是直接切换到大范围 grep。

## 4. 优化方向

这份报告聚焦一个更轻、更直接的改造方向：

- 不引入新的 `file_search` 工具
- 不引入复杂的索引或 session
- 不改变模型看到的工具集合
- 只优化 `glob_search` / `grep_search` 的底层实现和提示词引导

核心原则有两条：

> 1. 用 Node.js 自带的 `glob` 能力替换 `listAllContentFiles()`，让 `glob_search` 真正按路径模式匹配文件，而不是先枚举“有内容的文件”再过滤。
>
> 2. 强化 `glob_search` / `grep_search` 的提示词，引导模型先缩小文件范围，再做内容搜索，从而提升首轮命中率。

### 4.1 目标流程

建议把当前 `glob_search` 的宿主实现收敛成下面这条链路：

1. 模型调用 `glob_search`
2. `aily-lex` 仍然走宿主扩展 `host.getExtension('search').searchFiles(...)`
3. 宿主 `searchFiles()` 直接调用 Node.js 自带 `glob`
4. `glob` 返回真实文件系统里的路径候选
5. 在宿主侧统一做：
   - 相对路径转换
   - `limit` 截断
   - 路径规范化
   - 可选排序
6. 结果直接返回给 `glob_search`

和当前方案相比，最大的变化是：

- 不再通过 `rg -l .` 推导文件列表
- 不再依赖“文件必须有内容”这一前提
- 不再先做“内容文件枚举”，再做“路径过滤”

### 4.2 为什么用 Node.js 自带 `glob` 更合适

这个优化方向的好处很明确：

1. 它和 `glob_search` 的工具语义一致。
   - 用户传入的是 glob pattern
   - `globTool` 执行的也是真正的 glob 匹配

2. 它比现在的 `listAllContentFiles()` 更完整。
   - 空文件可以匹配
   - 纯配置文件可以匹配
   - 不依赖文件内容是否可搜索

3. 它比“手写 `globToRegex + 遍历结果过滤`”更可靠。
   - 不需要自己维护 glob 语法兼容性
   - 减少边界错误

4. 它比引入新架构更轻。
   - 不需要新增搜索协议
   - 不需要大改 agent 工具体系
   - 不需要引入复杂索引层

### 4.3 `grep_search` 也需要一起优化，但重点是“收窄范围”

这次不建议重写 `grep_search`，但建议明确它的职责：

- `glob_search` 负责找可能相关的文件路径
- `grep_search` 负责在收窄后的文件集合里找具体内容

因此 `grep_search` 的优化重点不是换引擎，而是提升“配合 `includePattern` 后的命中率”：

1. 优先让模型先做一轮 `glob_search`
2. 从 `glob_search` 结果里总结出更小的 `includePattern`
3. 再执行 `grep_search`

例如：

- 先用 `**/*pin*map*`
- 再用 `grep_search(query="I2C", includePattern="**/*pin*map*")`

这样比直接在整个仓库里 grep 更容易高命中，也更省结果预算。

### 4.4 需要替换的核心点

当前最应该被替换的是这里：

- [../aily-lex/src/tools/glob/globTool.ts](/Users/xiewendao/Documents/aily/aily-lex/src/tools/glob/globTool.ts:1)
- [../aily-lex/src/tools/common/search.ts](/Users/xiewendao/Documents/aily/aily-lex/src/tools/common/search.ts:289)
- [src/app/tools/aily-chat/helpers/lex-agent-bootstrap.ts](/Users/xiewendao/Documents/aily/aily-blockly/src/app/tools/aily-chat/helpers/lex-agent-bootstrap.ts:1858)

当前逻辑是：

1. `searchFiles()` 调 `ripgrep.listAllContentFiles()`
2. `listAllContentFiles()` 用 `rg -l --max-count=1 .`
3. JS 侧再用 `globToRegex()` 过滤

目标逻辑是：

1. `glob_search` 的核心逻辑直接放在 `aily-lex` 的 `globTool` 中
2. `globTool` 直接调用 `tinyglobby` 按 pattern 返回真实文件路径
3. `globTool` 内部统一处理 ignore、去重、排序和 `maxResults`
4. `search.ts` 不再承担 `glob_search` 的核心实现，而继续服务 `grep_search`
5. 宿主层如果仍提供 `searchFiles()` 扩展，也不作为本次优化方案的主实现入口

### 4.5 建议的实现方式

建议把实现直接收敛到 `aily-lex` 内部，而不是再额外设计一层宿主 IPC。

推荐做法：

1. 在 [../aily-lex/src/tools/glob/globTool.ts](/Users/xiewendao/Documents/aily/aily-lex/src/tools/glob/globTool.ts:1) 中直接实现 `tinyglobby` 版本的 `glob_search`
2. 在 `globTool` 中统一处理：
   - 相对路径输出
   - 路径规范化
   - 去重
   - 排序
   - `maxResults` 截断
3. 把 ignore 规则抽成共享常量，供 `glob_search` 和 `grep_search` 一起使用
4. 保留 [../aily-lex/src/tools/common/search.ts](/Users/xiewendao/Documents/aily/aily-lex/src/tools/common/search.ts:289) 继续负责 `grep_search`
5. 继续允许宿主层保留自己的扩展能力，但不把它作为 `glob_search` 主实现的一部分

这样职责会更清楚：

- `glob_search`：`globTool + tinyglobby`
- `grep_search`：`search.ts + ripgrep`

### 4.6 建议的输入输出约束

`glob_search` 当前对外输入已经够用，不建议新增太多字段。

建议继续保留：

- `pattern`
- `cwd`
- `maxResults`

`globTool` 实现里建议统一做这些规则：

1. 返回相对路径，而不是绝对路径
2. 路径统一为 `/`
3. 严格执行 `maxResults`
4. 默认排除常见无关目录
5. 行为尽量稳定，不依赖扫描顺序的偶然性

### 4.7 ignore 规则建议

这里不建议一开始就做得很重，但至少要统一。

建议优先采用以下策略：

1. 默认排除：
   - `.git`
   - `node_modules`
   - `.cache`
   - `.aily`
   - `.aily_checkpoints`
   - `__pycache__`

2. 是否跟随 `.gitignore`
   - 如果 Node.js 当前 `glob` 方案能方便接入，则优先尊重
   - 如果当前运行时接入成本较高，可以先保持“显式排除目录”为主

3. 无论如何，都不要再混用：
   - “ripgrep 的内容文件枚举语义”
   - “手写目录遍历语义”

至少要保证 `glob_search` 只有一套稳定语义。

### 4.8 排序建议

不需要把排序做复杂，但建议至少不要继续依赖枚举顺序。

一个足够轻的排序策略是：

1. 先按路径深度升序
2. 再按文件名长度升序
3. 最后按路径字典序升序

这样通常能让：

- 更短的入口文件
- 更浅层的配置文件
- 更直观的目标文件

排在前面，结果会比“谁先扫描到谁在前面”更稳定。

### 4.9 fallback 建议

当前实现里 `searchFiles()` 在宿主扩展路径下还会 fallback 到文件系统遍历。

优化后建议：

1. `glob_search` 首选 `tinyglobby`
2. 如果 `tinyglobby` 失败，再 fallback 到较轻量的本地文件系统递归
3. fallback 时仍然只做“真实文件系统路径匹配”
4. 不再依赖 `listAllContentFiles()`

这样即使回退，语义也还是“找文件”，而不是“找有内容的文件”。

### 4.10 提示词引导建议

为了提高首轮命中率，建议同步修改 `glob_search` / `grep_search` 的提示词和工具描述，重点不是增加术语，而是增加可执行的搜索策略。

建议补充以下规则：

1. 当用户只给概念词时，优先把词拆成路径片段，再构造 glob。
   - 例如 `tool invocation formatter` 可转成 `**/*tool*invocation*formatter*`

2. 当用户要找“某类文件”时，优先加上扩展名或目录范围。
   - 例如 `**/*.md`
   - 例如 `src/**/*.ts`
   - 例如 `docs/**/pin*`

3. 当首轮 `glob_search` 无结果时，优先逐步放宽 pattern。
   - 从 `src/**/file-search*`
   - 放宽到 `**/*file-search*`
   - 再放宽到 `**/*search*`

4. `grep_search` 默认不应该直接扫全仓。
   - 先 `glob_search`
   - 再把 glob 模式或其结果映射成 `includePattern`

5. 当目标可能是配置文件、说明文档、入口文件时，优先尝试：
   - `**/*config*`
   - `**/*readme*`
   - `**/*index*`
   - `**/*main*`

## 5. 这样优化后会带来什么体验提升

### 5.1 `glob_search` 会真正符合直觉

优化前，用户以为自己在“按路径查找文件”，实际系统在“按内容文件候选集查找路径”。

优化后，用户传什么 glob，系统就按 glob 匹配真实文件路径。这会让结果更符合用户预期，也更符合工具名称。

### 5.2 空文件和配置文件不再天然丢失

这是最直接的体验提升。

例如这些文件在优化后都应该能稳定搜索到：

- `.env.local`
- `tsconfig.json`
- `README.md`
- `config/*.json`
- 空白占位文件

### 5.3 结果稳定性更高

优化前，结果是否出现，部分取决于：

- 文件有没有内容
- ripgrep 是否把它识别为内容文件
- fallback 有没有扫到它

优化后，结果只取决于：

- 路径是否匹配 glob
- ignore 规则是否排除它

这会让行为更可解释。

### 5.4 首轮命中率会更高

这次不引入新的工具，但只要做到两件事：

- `glob_search` 真正按路径查找
- 提示词明确引导“先 glob 收窄，再 grep 命中”

模型的首轮搜索命中率就会明显提高。

这比单纯增加工具数量更实际，因为问题的关键不是“缺工具”，而是“现有工具没有被正确实现和正确引导”。

### 5.5 维护成本更低

- 自己兼容 glob 语法
- 自己拼装不可靠的“内容文件候选集”
- 自己修很多路径边界问题

## 8. 结论

当前 `aily-blockly` 的文件查找问题，主要不是工具数量不够，而是两件基础工作没有做好：

- `glob_search` 的底层实现不对
- `glob_search` / `grep_search` 的提示词引导不够具体

也就是说，它并不是直接按路径做 glob，而是先通过内容搜索枚举一批文件，再在 JavaScript 里二次过滤；同时模型也缺少足够明确的“如何先缩小范围再命中内容”的指导。

如果只做一件事，最值得做的是：

> 用 Node.js 自带的 `glob` 替换 `listAllContentFiles()`，并补强 `glob_search` / `grep_search` 的提示词引导，让现有 `glob/grep` 体系能打出更高命中。

这是一个足够轻的优化方向，改动范围可控，但能直接改善：

- 空文件搜不到
- 配置文件搜不到
- 结果不稳定
- 工具行为与名称不一致
- 首轮搜索命中率不高
