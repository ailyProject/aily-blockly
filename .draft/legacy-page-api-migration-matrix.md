# Legacy 页面 API 迁移对照表

## 任务目标

梳理 legacy 路由页面使用的主要 API / host 能力，并映射到实验性重写项目里已经落到 `core` / `desktop` 的 RPC 或替代入口；同时标记哪些页面仍未完成迁移，或者当前只有占位实现，没有把 legacy 能力真正沉到 `core` / `desktop`。

## 基线与来源

- 基线文档：`REFACTOR.md`
- DeepWiki 索引：`.draft/legacy_deepwiki/README.md`
- legacy 路由：`/Users/xiewendao/Documents/aily/aily-blockly/src/app/app.routes.ts`
- legacy 页面实现：`/Users/xiewendao/Documents/aily/aily-blockly/src/app/...`
- 当前路由：`packages/ui/src/routes/main-routes.ts`、`packages/ui/src/routes/tool-routes.ts`、`packages/ui/src/routes/window-routes.ts`
- 当前 RPC：
  - `packages/core/src/rpc/*`
  - `packages/desktop/src/rpc/*`

## 判定口径

- 这里只统计“页面依赖的后端/宿主/云端/串口/文件系统/工具进程/API 能力”。
- 不把 `Router`、`ChangeDetectorRef`、`NgZone`、纯模板状态之类前端内聚逻辑算作 API。
- `app.routes.ts` 中注释掉的未来/预留路由不纳入本次“legacy 已存在页面”统计，例如 `ai-manager`、`sub`、`chipintelli`、`vision/pose`、`audio`。
- `状态` 定义：
  - `已迁移`：legacy 关键 API 已经有 `core` / `desktop` 对应承接。
  - `部分迁移`：已有主要 RPC，但仍缺关键 legacy 能力，或者能力已拆分但未闭环。
  - `占位/未迁移`：当前页面主要是静态展示、示例或健康检查，未覆盖 legacy 核心 API。
  - `已拆分迁移`：legacy 单页能力被拆到多个新页面或新 router。

## 当前判断

- 已经形成比较清晰的 `core`/`desktop` RPC 主干的页面：
  - `serial-monitor`
  - `child-tool`
  - `graph-editor`
  - `blockly-editor` 的文档/库/生命周期核心链路
  - `project-new` 的项目创建/模板导入主链路
- 仍明显属于“页面先占位，legacy API 还没迁完”的区域：
  - `settings`
  - `playground`
  - `model-deploy`
  - `model-train`
  - `simulator`
  - `code-viewer`
  - `iframe`
- 被“拆页迁移”的区域：
  - legacy Blockly 库管理 -> `lib-manager`
  - legacy 云项目/模板相关能力 -> `cloud-space` + `project-new`
  - legacy 构建/上传终端交互 -> `terminal`
