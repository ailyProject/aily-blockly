# Blockly 大项目加载与拖动性能分析

2026-10-10 起，宿主使用 `blockly: npm:aily-project-blockly@1.0.3`（上游 Blockly 13.3.0），本地发行包、补丁快照和源码同步入口均已移除。本文保留切换前的包哈希和性能记录；当前安装方式见 [开发人员须知](../develop.md#开发打包)。

## 本轮复查：加载、编辑与延迟刷新

继续使用同一 8,265 块真实项目（最大拖动栈 7,505 块），保留主题、图标和小地图。当前 Blockly 核心提交为 `154bdcad7`（包含加载优化 `3cfd8ca15`），串口库修复位于独立仓库 `aily-blockly-libraries` 的 `97250664`。下方“第一阶段记录”保留此前虚拟化实施过程及旧包数据，本节是本轮最终结果。

### 新发现与修改

- **加载存在重复的祖先/后代遍历。** JSON 子树初始化原来逐节点向全部祖先排队，又对已创建的后代反复关闭连接跟踪。现在每个节点先关闭自身连接跟踪，再加载后代；子节点只排队自身，完成子树后才更新既有父树。保留事件组、撤销语义和自定义初始化行为。
- **大量未初始化字段通过抛异常判断 ARIA 目标是否存在。** 内置字段现在直接判断字段组，第三方自定义焦点 getter 仍走原路径。
- **深层字段修改会为读取已有尺寸而重新挂载离屏祖先。** 内置干净字段复用尺寸，自定义尺寸 getter、全块输入字段及图标仍保留真实 DOM 测量。
- **外部串口库的延迟刷新打断首轮拖动。** 加载缩短后，一次首轮拖动暴露出 3.846 秒尾延迟，CPU 调用链是 `updateSerialBlocksWithCustomPorts → block.render → 整栈布局/样式读取`。库脚本原来遍历串口块逐个同步重绘，选项未变化也重绘。修复后只在值或当前显示标签变化时排队，批量刷新共用一次选项计算；有效串口值、引脚标签、删除自定义串口后的回退均保留。
- **后台代码生成占用连续主线程任务。** 复用同一次完整快照校验已生成的 canonical 文本，在背景预览的准备/校验/发布阶段之间让出任务队列。没有改成不可靠的事件计数缓存；异步间发生编辑、页面或运行时替换时仍拒绝旧结果。主动保存/构建的同步生成边界保留。
- **组合操作发现第二处 Chromium SVG 问题。** 虚拟化开关、折叠重载、深层编辑后，再让串口下拉文字变长，会使 3 个块的 SVG 属性与 `getCTM` 不一致。等待动画帧不能修复。把视口的同父重排也从 `moveBefore` 改成原生插入后，相同组合链路恢复 0 差异；现在所有视口挂载统一走普通插入，并保留活动焦点恢复。对照先改整个控制器原型，确保重新开启虚拟化后新建的控制器也使用同一路径，随后才落入源码和最终包。

## 拖动根因

主软件 17.77 秒拖动 trace 的主要阶段如下。`Document::rebuildLayoutTree` 属于 `UpdateLayoutTree` 的内部阶段，不能重复累加。

| 浏览器阶段 | 主软件原始 SVG | 浅层 SVG 实验第一次 |
| --- | ---: | ---: |
| 样式和布局树更新 `UpdateLayoutTree` | 8.85 秒 | 0.37 秒 |
| 其中布局树重建 | 8.14 秒 | 0.30 秒 |
| 布局 `Layout` | 2.88 秒 | 0.56 秒 |
| 合成分层 `Layerize` | 3.09 秒 | 0.44 秒 |
| 绘制 `Paint` | 0.64 秒 | 0.55 秒 |

独立页面复现了与宿主相同量级的卡顿；官方核心也复现。因此当前主要问题在大量、深层 SVG 的浏览器处理成本。Aily 既有迭代遍历、连接枚举和原子 DOM 移动已经减轻了 JavaScript 成本，但无法使浏览器跳过深层树的样式、布局和合成。

`BlockSvg.moveDuringDrag` 会移动 SVG 根并更新后代坐标；开始和结束拖动还涉及选择／焦点状态、换层与置顶。仅取消换层下降至 12.64 秒，仍保留大部分卡顿；取消拖动 class 或 `:has()` 规则也没有消除卡顿。继续只调 class、事件 debounce 或 `z-index`，预期收益有限。

图标是明确的放大因素：Aily 渲染器带来 7,993 个 `foreignObject`，SVG 子元素由标准渲染器的 89,585 增至 113,564。隐藏它们或改用标准渲染器都减少了耗时，但仍然需要十几秒。浅层 SVG 实验保留了这些图标和全部节点，仍大幅减少样式树重建，进一步区分了节点内容与嵌套结构的影响。

## 加载根因

加载既有浏览器成本，也有 JavaScript 的批量创建与重复检查成本。主软件加载 CPU profile 中可定位的热点包括：

- `primeBlocklyTextWidths` 的字体样式读取约 1.51 秒；实际渲染中的下拉文本测量仍约 0.79 秒。批量测量有收益，但并没有消除所有样式读取。
- `blockly-declarative-block-catalog.ts` 的 `intact` 检查累计约 1.47 秒，调用链包括 `assertCurrent → nativeFieldOrder → restoreNativeFields`。完整已使用类型集合的校验在大量字段恢复过程中反复出现。
- 核心 `queueBlock` 向祖先递归排队约 0.90 秒，`setConnectionTracking` 遍历后代约 0.90 秒。长链会增加重复祖先／子树访问。
- 大量 SVG `appendChild` 和 `setAttribute`，以及原生样式／布局处理，构成另一部分负担。这些采样量用于识别热点，不能直接相加为完整加载时间。

另一个结构诊断保留全部 8,265 块、字段与图标，将 `next` 长链拆成多个顶层短栈，最大 SVG 深度变为 7，首次可见降至 3.02 秒。该操作改变了程序拓扑和顶层执行顺序，不能用于优化用户项目；其拖动目标也只剩 16 块，因此 1.33 秒的拖动结果不参与整栈速度比较。它只用于佐证深度对加载的影响。

## 优化实施顺序

1. **优先在 Blockly 核心建立浅层 SVG 渲染方案。** 保留语义上的父子关系，独立维护显示层的父节点和坐标。实验中处理整棵根栈后的坐标同步是必要条件：最初的简单扁平化虽然变快，却导致 2,115 个坐标不一致，已判为失败；有效版本在每次根节点位置更新后同步显示坐标，且跳过没有变化的 transform 写入。
2. **逐步降低图标成本。** 可以试验 SVG path 或字体 SVG text，保留现有图标、颜色、可点击入口和字体加载行为。不能用删除图标的诊断数字作为已完成优化。
3. **改进加载批次。** 优先研究渲染排队的重复祖先访问、连接跟踪批次，以及字段恢复中重复的声明一致性校验。需要保留事件组、撤销、动态字段重建和库注册变更的检测，不能直接取消校验。
4. **对超大可见工作区再考虑视口裁剪或分区渲染。** 浅层结构仍有十万级 SVG 子元素；3 秒级整栈拖动还不能称为流畅。小地图已有 Worker/Canvas，不等于主工作区已经虚拟化。

在诊断阶段，浅层 SVG 代码只位于性能夹具的 `diagnostic=flat-svg` 分支。产品接入需要验证拖出中间块、拆接和吸附、折叠展开、拖入工具箱删除、变量／字段编辑、键盘和屏幕阅读器焦点、气泡和 mutator、多选、撤销重做，以及保存重新打开后的几何一致性。该诊断阶段的成功证据限定为真实鼠标整栈移动。

## 视口虚拟化可行性评估（实施前）

2026 年 10 月 9 日追加评估：**可以改造，且值得优先验证“浅层 SVG + 块级视口裁剪”。** 现有版本没有可直接打开的主工作区虚拟化开关。改造涉及 Blockly 核心和宿主插件，单独替换主题、renderer 配置或套用 Angular 列表虚拟滚动不能解决当前长栈问题。以下保留实施前的源码审查和视口密度测量结果；实施后的证据见文首新增章节。

### 本项目是否存在足够的裁剪空间

在现有浅层 SVG 实验页面中，保留完整 8,265 块模型，缩放为 1，工作区视口为 1,440 × 756。在最大栈的顶部、25%、50%、75% 和底部取样，使用缓存的 `getBoundingRectangleWithoutChildren()` 计算块本体边界与视口的相交关系；没有修改用户项目，也没有删除块。该边界包含跨越可见区的长 C 形块，但不把后续 `next` 栈作为自身边界。它是挂载候选估算，不是像素可见性判定。

| 最大栈滚动位置 | 与视口相交的块边界 | 各侧扩展 400px 后的候选块 | 保留全部逻辑祖先后的数量 | 仅做顶层栈裁剪仍需保留 |
| --- | ---: | ---: | ---: | ---: |
| 顶部 | 36 | 81 | 56 | 7,550 |
| 25% | 37 | 73 | 878 | 7,505 |
| 50% | 44 | 90 | 1,008 | 7,505 |
| 75% | 70 | 134 | 1,056 | 7,505 |
| 底部 | 106 | 190 | 1,346 | 8,220 |

本次只抽样这五个位置和一个缩放比例；没有证明所有位置都只需 190 块。气泡、阴影、图标溢出、连接预览和活动编辑器还需额外保留。缩小视图后会同时看到更多内容，虚拟化收益会下降。

当前项目只有 3 个顶层块，最大栈占全部块约 90.8%，所以按顶层块隐藏的收益很有限。直接沿用嵌套 SVG 并保留可见块的祖先，底部仍需保留 1,346 个块及深层容器。这是先解除显示树与逻辑父子树绑定的重要理由。原始数据在 `e2e/.artifacts/blockly-causal-2026-10-09/virtualization-density.json`，取样前后块数和生成代码均一致。

### 方案取舍

| 方案 | 对当前长栈的价值 | 改造成本与限制 |
| --- | --- | --- |
| 顶层栈 `display:none` 或函数分组 | 有助于分散的多个小栈；难以解决当前 7,505 块主栈 | 较低；本项目已有函数视图隐藏机制，但它不是块级视口虚拟化 |
| 在现有嵌套树上逐块隐藏 | 可以减少部分绘制，但父块隐藏会连带隐藏可见后代 | 中等；需保留祖先容器，深层结构问题仍在，不能把它作为最终方案 |
| 浅层 SVG + 可见块挂载/移出活动 DOM | 推荐；同时减少 DOM 深度和参与浏览器渲染的节点量 | 中高；初期可保留离屏 SVG 对象，改善持续交互，不能消除初次全量构建成本 |
| 完整模型与视图生命周期分离，按需创建视图 | 冷启动和 DOM 内存也有进一步优化空间 | 高；需要字段测量、序列化初始化、动态 mutator 和插件契约改造 |

### 必须处理的源码耦合

### 建议的实施边界与验收

1. **先完成浅层显示树的正确性。** 逻辑块树、变量、事件、撤销和生成器维持完整；建立显示父节点与逻辑父节点的独立关系。通过中间块拆接、多选、折叠、焦点和保存重开验证后，才接入裁剪。
2. **实现保持完整模型的动态块级裁剪。** 视口加预加载边缘查询缓存索引，仅更新进出集合。按帧合并查询，避免每个指针事件扫描全部 8,265 块。初期可以保留离屏 DOM 对象引用，只移出活动树，并设缓存策略；这一步主要改善平移、缩放及拖动，内存和首屏收益有限。
3. **适配巨大整栈拖动。** 被拖模型仍含全部 7,505 块，但只挂载视口内和必要交互视图；拖动栈采用局部索引和根变换。不能开始拖动时又把整个栈挂载回来。越过视口边缘和自动滚屏时应增量更新，松手后的连接/布局结算不能产生另一段秒级停顿。
4. **再处理首屏和按需建图。** 优化声明校验与布局批次；为标准字段建立独立测量/缓存，按字段类型兼容自定义扩展。持久布局缓存需按主题、字体、语言、渲染器、库版本、字段值和 mutator 状态失效。Worker 可承接纯几何/索引计算；现有依赖 DOM 的字段逻辑不能直接搬进 Worker。

建议使用 Blockly 模式内的实验开关逐步接入，不改变 ABI 项目文件和生成代码格式，并保留原生路径用于对照与回退。是否默认开启以实际回归为准，而不是只按块数决定。

性能验收要分别记录冷加载/首屏、持续手势的逐帧时间、长任务、松手结算、挂载节点量和内存。固定视口下扩大离屏项目时，挂载量应主要随可见复杂度变化。可将典型拖动 p95 帧间隔不超过约 33ms、可见区切换没有空白或反复长任务作为待验证的第一阶段目标，不能视为本次已达到的结果。

功能验收覆盖：拖出中间块、吸附和插入预览、跨视口拖动及自动滚屏、快速平移缩放、折叠展开、函数视图、框选多选、字段/气泡/IME、键盘和屏幕阅读器、搜索定位、删除/撤销/重做、AI 批量修改、保存重开、小地图及全量图片导出。以块模型、生成代码和实际挂载块坐标一致性作底线检查；未挂载块则检查缓存几何与连接索引，不能再要求其 DOM `getCTM()` 存在。

评估结论是“技术可行、裁剪空间充分、值得做分阶段核心改造”。此前浅层 SVG 的约 80% 改善是已有实测；新增视口统计不能推导出 60 FPS、加载 1 秒或再减少 99% 耗时。动态挂载开销、滚动时的缓存命中率、布局失效范围和宿主插件兼容仍需原型验证。
